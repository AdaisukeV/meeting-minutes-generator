description: 生成済みの議事録を元インプット・中間生成物と突き合わせ、漏れ・矛盾・要フォロー事項を指摘する
argument-hint: <project> <date>
allowed-tools: Read, Glob, Grep, Write
---

引数: `$ARGUMENTS`

上の引数を空白区切りで解釈し、1つ目を `{project}`(プロジェクト名)、2つ目を `{date}`(会議日 `YYYY-MM-DD`)として扱ってください。以降のファイルパス中の `{project}` / `{date}` はこの値に読み替えます(**位置引数の展開は呼び出し経路によって番号がずれることがあるため、本コマンドでは使わず、上の引数文字列を正として解釈する**)。引数が2つ揃っていない場合は、レビューを行わず `/minutes-review <project> <date>` の形式で指定するよう案内して終了してください。

## 前提

- **本コマンドは指摘のみを行う。議事録・中間生成物・元インプットを修正してはならない。** 修正は利用者が該当ステップを再実行して行う(`./scripts/generate_minutes.sh {project} {date} --only-step N`)。Write を使うのは**手順5のレビュー結果ファイル(新規パス)を作成するときだけ**。
- 議事録の生成は3段階パイプライン(ステップ1: 話者・発言の整理 → ステップ2: 会話の構造化 → ステップ3: 議事録フォーマット)であり、**情報はどの段でも落ちうる**。指摘には「どの段で落ちた/変質したか」を必ず併記する。

## 手順

1. 次のファイルのうち**存在するものすべて**を Read で読み込む(存在しないものは読み飛ばす。エラーとしない)。議事メモは固定名ではないため、`inputs/{project}/{date}/` の `*.md` / `*.txt` を Glob で列挙し、**見つかったものをすべて読む**(同一会議に対して自動生成メモ・手書きメモなど複数存在しうる。1つでも読み飛ばすと、そのメモにしか無い情報の欠落を検出できない)。

   | ファイル | 位置づけ |
   |---|---|
   | `inputs/{project}/{date}/*.md` / `*.txt` | 議事メモ(一次情報。**複数存在しうる**) |
   | `outputs/{project}/{date}/00_transcript.txt` | ローカル文字起こし(一次情報。録画が複数の場合は `----- TRANSCRIPT PART n/N: <ファイル名> -----` 区切りの連結) |
   | `outputs/{project}/{date}/01_speakers_utterances.md` | ステップ1の出力 |
   | `outputs/{project}/{date}/02_structured_conversation.md` | ステップ2の出力 |
   | `outputs/{project}/{date}/minutes.md` | 最終議事録(レビュー対象) |
   | `projects/{project}/config.yaml` | 話者・会社・議事録構成の定義 |

   `minutes.md` が存在しない場合、または上記が1つも存在しない場合は、レビューを行わず**不足している内容と次に実行すべきコマンド**(`./scripts/generate_minutes.sh {project} {date}`)を提示して終了する。

2. 一次情報(議事メモ / `00_transcript.txt`)→ ステップ1 → ステップ2 → `minutes.md` の順に**同じ事実を追跡**し、各段での欠落・変質を洗い出す。特に次を重点的に確認する。
   - **数値・日付・期限・金額・工数**が段をまたいで変わっていないか
   - 議事メモが複数ある場合、**一方のメモにしか書かれていない項目**が落ちていないか(どのメモが出所かを指摘に併記する)
   - メモ間で記述が食い違う箇所が、どちらか一方に確定されていないか(`(要確認)` で両方残すのが期待挙動)
   - 文字起こしが複数パートの場合、**後半パートの議題**が落ちていないか(パート境界で会議が終わったものとして扱われていないか)
   - **担当者**が入れ替わっていないか、`config.yaml` の `speakers[].name` の表記に統一されているか
   - 決定事項・依頼事項・宿題が `minutes.md` まで到達しているか
   - `(要確認)` / `(不明)` が段の途中で勝手に確定した内容に置き換わっていないか(**その逆に、確定していた内容が `(要確認)` に退化していないか**)
   - `minutes.md` の見出しが `config.yaml` の `minutes_sections[]` の順序・項目と一致しているか
   - 一次情報に無い事実が追加されていないか(ハルシネーション)

3. 以下のフォーマットで指摘を出力する。該当が無い節は `- 特になし` と書いて見出しは残す。

   ```markdown
   ## 1. 議事録から漏れている内容

   - <漏れている内容>(根拠: <一次情報の該当箇所> / 落ちた段: <ステップN の出力に無い、等>)

   ## 2. 矛盾点

   - <箇所A> と <箇所B> が矛盾(根拠: <どちらが一次情報と一致するか>)

   ## 3. 要確認・フォローアップ事項

   - <項目>(誰に何を確認すべきか)
   ```

4. 最後に、**再実行すべきステップの提案**を1〜3行で添える(例:「担当者の取り違えはステップ2で発生しているため `--only-step 2` から再実行を推奨」)。指摘が無い場合は「重大な指摘なし」と述べる。

5. 指摘結果を `outputs/{project}/{date}/review_{NN}.md` に保存する(画面出力と同じ内容)。

   - `Glob` で `outputs/{project}/{date}/review_*.md` を列挙し、**既存の最大の連番 +1** を2桁ゼロ埋めで使う(1件も無ければ `01`)。**既存ファイルを上書きしてはならない。**
   - ファイルの先頭に次のヘッダを置き、続けて手順3の3節と手順4の提案をそのまま書く。

     ```markdown
     # 議事録レビュー: {project} {date}(第{NN}回)

     - レビュー実施日: <今日の日付。分からない場合はこの行を省略>
     - 参照したファイル: <実際に読み込めたファイル名をカンマ区切りで列挙>
     ```

   - 保存したパスを最後に1行で伝える(例:`レビュー結果を outputs/{project}/{date}/review_01.md に保存しました。`)。
   - 保存に失敗した場合(権限が拒否された等)は、**画面への指摘出力は必ず完了させた上で**、保存できなかったことだけを伝える(レビュー結果を失わないことを優先する)。

## 指摘の基準

- **一次情報に根拠のある指摘のみを書く。** 「より詳しく書いた方が良い」といった一般的な改善提案は書かない(事実の欠落・矛盾・要確認に限定する)。
- 表記のゆれ・語尾の統一といった軽微な体裁は、意味が変わらない限り指摘しない。
- 逆に、**会議の意思決定に影響する欠落(期限・担当・金額・採否)は軽微に見えても必ず指摘する。**
- 一次情報自体が曖昧な箇所(`(聞き取れず)` 等)は、議事録側の欠陥ではなく「3. 要確認」に分類する。
