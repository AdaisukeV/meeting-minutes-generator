## 1. `CLAUDE.md` 混入に関する実機検証(要件3.2.7)

2026-08-16、`claude` CLI(Bedrock 経由)で検証。

| 実行条件(cwd = リポジトリルート) | プロジェクト固有指示の混入 |
|---|---|
| `claude -p --system-prompt-file <file> --tools ""` | **混入した**(`CLAUDE.md` のコミット禁止パス・`set -euo pipefail` 規約・パイプライン方針を原文引用できた) |
| `claude -p --bare --system-prompt-file <file> --tools ""` | 混入なし(`NO_PROJECT_INSTRUCTIONS`) |
| cwd をリポジトリ外にして `--system-prompt-file --tools ""` | 混入なし |

**結論**:`--system-prompt-file` はシステムプロンプトを置き換えるが、`CLAUDE.md` の自動読み込み(プロジェクトメモリ)は別経路で行われるため、それだけでは要件3.2.7を満たさない。よって [02-generate-minutes.md §5](./02-generate-minutes.md) のとおり **`--bare` の併用と、リポジトリ外の空ディレクトリでの実行を両方採用**する(二重防御)。要件3.2.5/3.2.7 の記述もこの内容へ更新することを提案する(§3)。

### 1.2 `--system-prompt-file` の互換性リスク(2026-08-16 実測)

`--system-prompt-file` は `claude --help`(**v2.1.233**)の一覧に**記載されていない**が、渡すと**受理され機能する**(上表の検証はすべてこのオプション経由で行った)。

```
$ claude --version
2.1.233 (Claude Code)
$ claude --help | grep -c system-prompt-file
0
```

- **リスク**:ヘルプ非記載のオプションは将来の CLI 更新で予告なく変更・削除される可能性がある。その場合、システムプロンプトの完全置き換えが効かず、要件3.2.5/3.2.7 が壊れる。
- **緩和策**:オプションの受け渡しを [02-generate-minutes.md §5](./02-generate-minutes.md) の `invoke_claude` 1箇所に閉じ込め、**渡す引数を bats のケース21で固定**する([07-testing.md §4](./07-testing.md))。CLI 更新でオプション名が変わった場合は、`invoke_claude` の修正のみで追従できる。
- **検知方法**:`claude` CLI を更新した際にケース21と、実機での `CLAUDE.md` 非混入チェック(§1の表)を再実行する。空出力・混入のいずれも `invoke_claude` がコード3、または混入チェックの失敗として現れる。

## 4. 同一会議の複数インプットへの対応(2026-08-17)

### 4.1 「暗黙の連結はしない」判断の撤回

当初([02-generate-minutes.md §6](./02-generate-minutes.md) の初版)は、メディアファイルが2件以上ある場合を **die(1)** としていた。根拠は「どの順序で連結すべきかをシェル側が推測すると、誤った時系列の文字起こしを黙って作ってしまう」ためで、利用者に1件へ絞らせる方針だった。

これを撤回し、**全件を文字起こしして連結する**方針へ変更した。理由は次のとおり。

- **会議を中断して録画を再開すると、1つの会議が複数ファイルに分割される**という運用が日常的に発生することが判明した(2026-08-17 に利用者から指摘)。この場合、複数ファイルは「別の会議」ではなく「同一会議の連続したパート」であり、1件に絞ることは情報の欠落を意味する。
- 従来の回避策(利用者が事前に `transcribe.py` を個別実行して `00_transcript.txt` を手で組み立てる)は、ステップ0を自動化した要件3.1の意図に反する。
- 誤った順序への懸念は、**順序規則を `LC_ALL=C` のファイル名昇順に固定し、連結順を進捗出力に列挙する**ことで緩和する。推測ではなく明示された規則であり、利用者が実行時に検証できる。

議事メモ側も同様に `memo.md` 固定を撤回した。こちらは die すらせず、`memo.md` 以外のメモが**無言で無視される**挙動だったため、より深刻だった(議事録に情報が落ちたことに気づけない)。

### 4.2 パートのタイムスタンプをオフセットしない

分割録画の各パートは `[00:00:00]` からタイムスタンプが振り直される。連結時に「前パートの長さを累積して足す」という選択肢を検討したが、採用しない。

- 分割の原因は**会議の中断**であり、パート間には実時間の空白がある。累積オフセットは「パートが隙間なく連続している」という誤った前提に立ち、**存在しない時刻を捏造する**ことになる(要件3.2.4のハルシネーション防止と同じ性質の問題)。
- 空白の長さはファイルのメタデータからは分からない。
- ステップ1はタイムスタンプを出力しない(`prompts/01_organize.md` の禁止事項)ため、絶対時刻を保つ実利が小さい。時系列はファイル内の出現順で十分に表現できる。

代わりに `----- TRANSCRIPT PART n/N: <ファイル名> -----` のマーカーでパート境界を明示し、プロンプト側に「パートをまたいでタイムスタンプを比較しない」ことを明記する。

### 4.3 パートキャッシュを設けた理由

`faster-whisper` の実行時間が長いため、録画を1本追加するたびに全パートをやり直すコストが実運用で無視できない。メディアの basename をキーに `outputs/{p}/{d}/00_transcript_parts/` へパート単位の結果を残し、既存パートは再利用する(§6.1)。

`00_transcript.txt` が既存ならステップ0を丸ごとスキップする挙動(要件3.1)は変更していない。パートキャッシュが効くのは「録画を追加するために `00_transcript.txt` を削除して再実行したとき」である。

## 5. ステップ1・2の分割と並列実行(2026-08-18)

### 5.1 契機:コンテキスト上限ではなく所要時間

実プロジェクト(`projects/{project-name}`)の運用(2026-08-17 の会議、入力 約199KB / 76,000字)で、ステップ1が終わらないように見え利用者が `Ctrl+C` で中断した。調査の結果、**タイムアウトではなく中断**であり、`ERROR: claude の実行に失敗しました(step 1)` は SIGINT の終了コード130を `run_step` が「非ゼロ終了」として扱った結果にすぎなかった(この誤報自体の是正は [01-conventions.md §4](./01-conventions.md))。

ただし待ち時間は実在する。ここで重要なのは**律速が入力サイズではなく出力トークンの逐次生成**である点。

| ステップ | 出力の性質 | 出力量 |
|---|---|---|
| 1 | 全発言を1行ずつ書き直す(`prompts/01_organize.md`) | 入力と同規模 |
| 2 | `### やり取り` で全発言を役割付きで再掲(`prompts/02_structure.md`) | ステップ1と同等以上 |
| 3 | 構造化結果から議事録へ凝縮 | 小さい |

したがって:

- **分割を直列で実行しても短縮しない。** 生成する総トークン量は変わらず、各チャンクへ議事メモを再添付する分だけ入力が増えるため、むしろ遅くなる。§2の旧方針(「分割は将来拡張、当面は WARN」)は「分割すれば速くなる」という前提を暗に含んでいたが、これは成立しない。
- **短縮は並列実行によってのみ得られる。** 実時間は概ね並列度分の1になる。
- **ステップ3は並列化しない。** 出力が小さく律速ではない。連結後に単発で実行する。

### 5.2 オーバーラップを重複除去ではなく専用ラベルで扱う

チャンク境界で話者の推定・応答関係の手がかりが失われるため、境界前後に重なり(既定30行)を持たせる。重なりの扱いには2案あった。

| 案 | 内容 | 採否 |
|---|---|---|
| A | 重なりも通常の本体として渡し、**連結時に機械的に重複除去**する | **不採用** |
| B | 重なりを `CONTEXT_BEFORE` / `CONTEXT_AFTER` という**別ラベル**で渡し、出力してはならない範囲であることをプロンプトで明示する | **採用** |

A を採らない理由:ステップ1・2の出力は**入力の逐語コピーではない**(フィラー除去・表記統一・口語→書き言葉の整形が入る)。同じ発言が重なり側とチャンク側で異なる文面になるため、機械的な重複判定が成立しない。閾値を緩めれば別の発言を誤って削り、厳しくすれば重複が残る。**どちらの誤りも「発言の取り違え・欠落」であり、要件3.2.4のハルシネーション防止に反する。**

B の代償は「プロンプトが指示を守ることに依存する」点である。これは連結処理をゼロにできる利点と引き換えに受け入れる。守られなかった場合の検知は `/minutes-review`(重複の指摘)に委ねる。

同じ理由で `PART_INFO` を明示セクションにし、`会議情報` ブロックを先頭パートのみが出力するよう**プロンプト側で判定させる**(スクリプト側で後から重複ブロックを削らない)。

### 5.3 並列度の既定を 1 にした理由

- Bedrock の `ThrottlingException` は並列度を上げるほど起きやすく、**上げすぎるとかえって遅くなる**(失敗したリクエストの時間が丸ごと無駄になる)。適正値はアカウントのクォータ次第で、スクリプト側から知る手段がない。
- 既定を 1 以外にすると、既存利用者の実行がスロットリングで失敗する形の**後方非互換**になる。
- よって並列実行は**明示的なオプト・イン**(`--parallel N`、範囲 `1..8`)とし、README では 4 程度から試すよう案内する。
- スロットリングの自動リトライは実装しない。失敗はコード3で報告し、利用者が並列度を下げて再実行する。**完了済みのパートは `01_parts/` / `02_parts/` のキャッシュで再利用されるため、やり直しは失敗したパートのみ**になり、リトライ機構を持たない代償は小さい([02-generate-minutes.md §9.4](./02-generate-minutes.md))。

### 5.4 採らなかった分割方針

| 案 | 不採用の理由 |
|---|---|
| トピック単位の分割 | トピック境界を知るには先に会議全体を読む必要があり、**それ自体がステップ1・2と同じコストの処理**になる。行数分割は境界の質は劣るが、オーバーラップ(§5.2)で補える。 |
| 段階的要約(map-reduce の reduce 側で圧縮) | ステップ1・2は要約ではなく**全発言の保持**が目的(要件3.2.1)。圧縮は情報の欠落そのものであり、要件に反する。凝縮はステップ3で行う。 |
| 議事メモも分割する | 話者の名寄せ・固有名詞の確認に全チャンクで必要。分割すると、メモに名前が出てこないチャンクで話者が特定できなくなる。分割対象は1ファイルに限定し、他のメモは全チャンクへ全文添付する。 |
| ステップ1のパート出力をそのままステップ2のパート入力にする(境界の引き継ぎ) | `--from-step 2` / `--only-step 2` では `01_parts/` が無いため分割できず、**ステップ単位の部分再実行(要件3.2.5)と噛み合わない**。またステップ1・2で並列度を変えられない。代わりに「各ステップは自身の入力のうち最大の1ファイルを行数分割する」という単一の規則に統一した([02-generate-minutes.md §9.1](./02-generate-minutes.md))。 |
| 分割対象をスクリプトが内容から自動判定する | 「`00_transcript.txt` があればそれ、無ければ最大バイト数のメモ」という**明示された規則**とし、選択結果を実行時に表示する。§4.1 の連結順表示と同じ思想(推測ではなく規則、利用者が実行時に検証可能)。 |

### 5.5 ステップ別モデルIDを導入した理由

ステップ1はフィラー除去・表記統一・話者の名寄せという**機械的な処理**が主であり、判断の重さはステップ2・3にある。ステップ1のみ軽量なモデルへ振れると、出力量が最大のステップの単価と速度を改善できる。

- `ANTHROPIC_MODEL_STEP1` / `_STEP2` / `_STEP3` を任意設定とし、未設定のステップは `ANTHROPIC_MODEL` へフォールバックする。`require_model` は変更せず、**`ANTHROPIC_MODEL` はフォールバック元として必須**のまま残す(全ステップ分を書かせない)。
- エイリアス(`sonnet` 等)を書かずモデルIDを明示する方針(要件3.4)、認証経路ごとの分岐を持たない方針(`CLAUDE.md` 4章)は維持する。環境変数を読むだけの実装に留める。
- 実装は `step_model` 1関数に閉じ、`invoke_claude` は第4引数でモデルIDを受け取る([02-generate-minutes.md §5.1](./02-generate-minutes.md))。`claude` 呼び出しを1箇所へ閉じ込める構造(§1.2 の緩和策)は崩さない。

## 6. 実データでの初回実行から得た知見(2026-08-18 実測)

`--parallel 4` を実データ(76,000字・1,338行の文字起こし + 議事メモ3件)に適用した最初の2回はいずれも失敗し、次の3点が判明した。設計の前提を修正した箇所を記録する。

### 6.1 律速の正体は「1回の呼び出しの出力トークン上限」だった

- 失敗したパートは 35〜36分走ったのち `API Error: Claude's response exceeded the 32000 output token maximum.` を返していた(exit 1)。**スロットリングでもタイムアウトでも入力サイズ超過でもない。**
- 分割で下げるべき値は入力量ではなく**1パートの出力量**である。ステップ1・2は全発言を書き直すため出力量が入力量に比例し、粗い分割では上限に当たる。対処は `--parallel` を増やすか `CLAUDE_CODE_MAX_OUTPUT_TOKENS` を上げるかの2択([02-generate-minutes.md §9.6](./02-generate-minutes.md))。
- 上限超過が**エラーとして表に出るのは一部の経路だけ**である。`claude` が上限に当たった応答を自動継続した場合は成功扱い(exit 0)で不完全な出力が確定する(§6.5)。当初「上限超過はエラーなので切り詰めは起きない」と判断したが、これは誤りだった。
- 同一のパートが4並列では失敗し、2並列では成功した(出力 14,642 バイト)。生成の冗長さは実行ごとに揺れるため、**上限付近では成否が非決定的**になる。並列度を上げてパートを小さく保つ方が安定する。

### 6.2 失敗時に `tmp_out` を消していたため原因が残らなかった

`claude` は API エラーを **stdout** へ書く。stdout は `tmp_out` へリダイレクトしているため、失敗時に消すと**唯一の手がかりを自分で捨てる**ことになっていた(35分待って `ERROR: パート 1/4 の生成に失敗しました` だけが出る状態)。`preserve_failure_output` で `<確定先>.error.log` として残す設計に改めた([02-generate-minutes.md §5.4](./02-generate-minutes.md))。**外部コマンドの stdout をファイルへ捨てる経路では、失敗時にその内容を保全する。**

### 6.3 文字起こしを `00_transcript.txt` へ「コピー」しても議事メモ扱いは消えない

`inputs/` の `.txt` は `find_memo_files` が拾うため(§4 のラベル体系)、`text_gemini.txt` を `outputs/{p}/{d}/00_transcript.txt` へコピーすると **`MEETING_MEMO` と `TRANSCRIPT` の二重添付**になる。分割時は分割対象以外のメモが全パートへ全文添付されるため、1パートの stdin が 250KB(単発実行の 199KB より大)まで膨らんでいた。

- 当面の運用は**コピーではなく移動**(`inputs/` 側から `.md`/`.txt` 以外の名前へ退避する)。これで1パートの stdin は 96KB に下がった。
- 恒久対処(文字起こし相当のテキストを `inputs/` 側で区別する仕組み)は未着手。要件2のインプット定義に関わるため、要件定義書の更新を伴う別タスクとする(§2 の未決事項)。

### 6.4 `Opus 5 not available` の警告は `--model` の指定とは無関係

実行のたびに `Warning: Opus: Opus 5 not available — using Opus 4.7 / 4.8 / Sonnet 4.5 ...` が **stderr** へ出るが、`ps` で確認したところ `--model global.anthropic.claude-sonnet-4-6` は正しく渡っており、警告の内容も呼び出しごとに揺れる。`claude` CLI のセッション既定モデルに関する表示であり、リクエストに使われるモデルは `--model` が決める。**スクリプト側の対処は不要**と判断する(利用者が混乱しないよう README に注記する)。

### 6.5 `claude -p` は自動継続した応答の**最後のメッセージだけ**を返す

通し実行(exit 0)で得た `minutes.md` に `## 会議概要`〜`## 次回アクション` が一切無く、本文の途中(`続行で。(サンプルソフト)`)から始まる欠損が発生した。`claude` CLI のセッションログ(`~/.claude/projects/<実行時の一時ディレクトリ>/<session>.jsonl`)を確認したところ、ステップ3の1回の呼び出しは**4つの assistant 応答**に分かれていた。

| # | `stop_reason` | `output_tokens` | 本文の長さ |
|---|---|---|---|
| 1 | `max_tokens` | 64,000 | 0(thinking のみ) |
| 2 | `max_tokens` | 64,000 | 0(thinking のみ) |
| 3 | `max_tokens` | 64,000 | 12,040字(`# 議事録` から始まる**正しい先頭**) |
| 4 | `end_turn` | 7,871 | 8,540字(`続行で。(サンプルソフト)` から始まる継続部分) |

- `-p`(非対話)の結果として stdout へ出るのは**最後の応答の本文のみ**であり、3番目の 12,040字(会議概要・決定事項・ToDo・詳細議事録の前半)は**捨てられた**。
- したがって「上限に当たる」の帰結は2通りある。**(a) API エラーになって exit 1**(§6.1・`*.error.log` に残る)、**(b) CLI が自動継続して exit 0 のまま先頭が失われる**。危険なのは (b) で、`invoke_claude` の空出力チェックも終了コード判定も通過するため、**検知には別の手段が必要だった**。
- 同じ欠損はステップ1・2のパートでも起こり得る。今回の成功したパートはいずれも本文を持つ応答が1つだけだったため無害だったが、`STEP1_OUTPUT part 4/4` の失敗回には本文を持つ応答が2つ現れており、条件は同じである。

#### 採った対処:出力の先頭行の検証(2026-08-18 実装)

**出力の1行目が Markdown の構造的な行かどうかを照合し、不一致なら生成物を確定せず失敗させる**([02-generate-minutes.md §5.5](./02-generate-minutes.md))。自動継続は行の途中から再開するため、先頭行を見れば (b) を確実に捕まえられる。

- 契約は**プロンプト側に既にあった**(`01_organize.md` / `02_structure.md` の「出力の1行目は `## 会議情報` か…」、`03_format.md` の「出力の1行目を `# 議事録:` で始める」)。新しい規約を増やしたのではなく、既存の契約を機械検証の対象にしただけである。
- **見出しの文言では判定しない**(ステップ1・2は `^(#{1,6} |- )`、ステップ3は `^# `)。プロジェクトが `prompts/*.md` の見出し語を変えても誤検知しないため。実データ10ファイルで全一致、壊れた `minutes.md` のみ不一致を確認した。
- 終了コードは 3 のまま(内部戻り値 4 は `invoke_claude` → `die_step_failure` の間だけで使う)。[01-conventions.md §4](./01-conventions.md) の終了コード体系は変えない。
- 部分出力は `<確定先>.truncated.md` へ退避する。`.error.log`(エラーメッセージ)とは性質が違うため分ける。

**採らなかった案**

| 案 | 不採用の理由 |
|---|---|
| `--output-format json` の `num_turns` を見る | 1呼び出しが複数ターンに分かれたことを直接検知できるが、**外部の YAML/JSON パーサを使わない方針**(要件3.2.6・`CLAUDE.md` 3章)と衝突する。先頭行の検証で同じ欠損を捕まえられるため、依存を増やす価値がない |
| セッションログ(`~/.claude/projects/**/*.jsonl`)の `stop_reason` を読む | CLI の内部ファイル形式に依存し、更新で壊れる。今回の原因究明には有効だったが、**パイプラインには組み込まない** |

**併せて行った予防**(検知だけでは待ち時間が無駄になるため、上限に当たる確率自体を下げる)

- `CLAUDE_CODE_DISABLE_THINKING` の案内(§6.6。実測で最も効いた設定)。
- ステップ3の出力量削減:`minutes_sections` の `詳細な議事録(発言者・発言内容)` はステップ2の全発言を再掲するため出力が最大になる(実測でステップ3の出力の69% = 14,241字 / 20,580字)。**ステップ3の分割は「会議全体を1回で読む必要がある」という §5 の判断と衝突するため、節ごとの分割ではなくこのセクションの扱いを見直した。** 実プロジェクト側の `config.yaml` からは外し、経過は `02_structured_conversation.md` を参照する運用(`_template` の既定方針)に戻した。`_template` 側には、このセクションを追加すると上限に当たりやすくなる旨の注意を書いた([05-project-assets.md §2.3](./05-project-assets.md))。

### 6.6 所要時間の大半は thinking に消えていた

§6.5 の表のとおり、ステップ3では**本文を1文字も出さない応答が2回**(合計 128,000 出力トークン)発生し、これが41分の大半を占めていた。ステップ1の失敗パートも `max_tokens` の thinking のみの応答を4回繰り返した末にエラーになっている。

- **出力トークン上限は thinking と本文で共有される。** `CLAUDE_CODE_MAX_OUTPUT_TOKENS` を上げても thinking が食い潰せば本文は伸びず、継続が増えて §6.5 の欠損を招きやすくなる。
- 本アプリのステップ1〜3は「規則どおりの書き換え・整形」が主であり、長い思考を必要としない。導入済みの `claude` バイナリは `MAX_THINKING_TOKENS` と `CLAUDE_CODE_DISABLE_THINKING` の両方を認識する(バイナリの文字列で確認)。

#### 実測(2026-08-18・実プロジェクトの 2026-08-17 のステップ3を同一入力で3回)

| 試行 | 設定 | 結果 | 所要 |
|---|---|---|---|
| 1 | `MAX_THINKING_TOKENS=8000` | `API Error: Connection dropped (ECONNRESET)` → exit 3 | 38分 |
| 2 | `MAX_THINKING_TOKENS=8000` | `API Error: Can't reach the API server (ENOTFOUND)` → exit 3 | 27分 |
| 3 | `CLAUDE_CODE_DISABLE_THINKING=1` | **成功**(`end_turn` の応答1つのみ・出力5,252トークン・本文5,748字・thinking 0字) | **1分52秒** |

- **`MAX_THINKING_TOKENS` は効果が確認できなかった。** 試行2のセッションログでは 8000 を指定していたにもかかわらず、`max_tokens` で打ち切られた 32,000 出力トークンの応答が2回現れ、いずれも本文0字・thinking 約22,000字だった。上限として尊重されていない。
- **`CLAUDE_CODE_DISABLE_THINKING=1` は明確に効いた。** thinking が消えたことで応答が1回で収まり、自動継続そのものが起こらなくなった。§6.5 の欠損は「自動継続が起きたとき」にしか発生しないため、これは検知(先頭行の検証)と別に**発生確率を直接下げる**予防になっている。所要時間は 41分 → 1分52秒。
- したがって案内は `CLAUDE_CODE_DISABLE_THINKING=1` を主とし、`MAX_THINKING_TOKENS` は「効果が確認できていない」旨を添えて併記するだけに留める。
- どちらもスクリプトに新しい分岐を増やさない方針(`CLAUDE.md` 4章)に沿い、**`active.env` に書ける環境変数として案内するだけ**にする(`CLAUDE_CODE_MAX_OUTPUT_TOKENS` と同じ扱い)。スクリプトは参照しない。

> 試行1・2の失敗はいずれもネットワーク層のエラーだが、**42分近く1つの応答を待ち続けたこと自体が原因側**である(長時間の接続が切れやすい)。thinking を止めて所要時間が1/20になったことで、この失敗も併せて解消した。
