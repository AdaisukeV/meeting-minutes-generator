## 1. `config.yaml` スキーマ(要件3.2.4, 4)

シェルはパースしない。**LLM 向けのプロジェクト固有コンテキスト**として全文が stdin に添付される([02-generate-minutes.md §4](./02-generate-minutes.md))。したがってスキーマは「LLM が読んで解釈できること」を要件とし、厳密な型検証は行わない。

| キー | 型 | 必須 | 用途 |
|---|---|---|---|
| `project` | string | ✓ | プロジェクト表示名 |
| `companies[]` | list of `{name, short_name, role}` | ✓ | 会社名・略称・立場(自社/顧客/協力会社) |
| `speakers[]` | list of `{name, role, company, aliases[]}` | ✓ | 話者の名寄せ用(ステップ1) |
| `topic_guidelines` | string | – | トピック分類の粒度・観点(ステップ2) |
| `minutes_sections[]` | list of string | ✓ | 議事録の見出し構成(ステップ3) |
| `style` | `{tone, person, tense}` | – | 文体・敬体/常体等(ステップ3) |
| `notes` | string | – | 補足(専門用語・略語の対応など) |

雛形とは別に、動作確認用のダミープロジェクト **`projects/sample/`**(`config.yaml` + `prompts/` は `_template` のコピー)を Git 管理下に置く。内容は架空の会社・人物のみで構成し、対応する入力(`inputs/sample/{date}/memo.md`)は Git 管理外とする。プロンプト調整の効果を実機で確認する際の基準プロジェクトとして使う。

**Git 管理の範囲**:`projects/` 配下で追跡するのは `_template/` と `sample/` の2つのみで、**実プロジェクト `projects/{project-name}/` は Git 管理外**とする([06-security.md §1](./06-security.md))。`speakers[].aliases` は文字起こしの表記ゆれを寄せるために実在の個人名を列挙する前提であり、`companies[]` も実在の顧客名を含むため、雛形と同じ扱いにはできない。`generate_minutes.sh` は `projects/{name}/` の実ファイルの存在のみを検査するため([02-generate-minutes.md](./02-generate-minutes.md) の `validate_project()`)、Git 管理外でもパイプラインの動作には影響しない。実プロジェクトの設定を別環境へ持ち運ぶ場合は、リポジトリ経由ではなく利用者が個別に複製する。

**`_template/config.yaml`(記入例つき雛形)**

```yaml
# プロジェクト固有設定。generate_minutes.sh はこのファイルをパースせず、
# 内容をそのまま各ステップのプロンプトへコンテキストとして渡す。
project: サンプル案件

companies:
  - name: 株式会社サンプル
    short_name: サンプル社
    role: 顧客
  - name: 自社株式会社
    short_name: 自社
    role: 自社

speakers:
  - name: 山田 太郎
    role: 部長
    company: 株式会社サンプル
    aliases: ["山田", "山田さん", "ヤマダ"]
  - name: 鈴木 花子
    role: PM
    company: 自社株式会社
    aliases: ["鈴木", "鈴木さん"]

topic_guidelines: |
  アジェンダ単位でトピックを分ける。技術的検討と契約・スケジュールの話題は分離する。

minutes_sections:
  - 会議概要
  - 決定事項
  - 検討事項(要件・目標値・見積)
  - ToDo(担当者・期限)
  - 懸念事項
  - 次回アクション

style:
  tone: 敬体(です・ます)
  person: 三人称
  tense: 過去形

notes: |
  略語:SS=サブシステム、UT=単体テスト
```

## 2. `prompts/*.md` の設計(要件3.2.4)

`--system-prompt-file` は1ファイルしか指定できず、ファイル間の include もできない。よって**共通ルール(要件3.2.4)は3ファイルそれぞれに自己完結で記載する**(重複を許容する)。重複を嫌って共通部分を外部化すると、シェル側でプロンプト結合ロジックが必要になり「システムプロンプトの完全置き換え」の単純さを損なうため、KISS 原則(要件8.1)を優先する。

各プロンプトの節構成(3ファイル共通):

```markdown
# 役割
(このステップで何をするか)

# 入力の形式
stdin に `===== INPUT: <ラベル> (<ファイル名>) =====` 区切りで与えられる。
扱うラベル:…

# 共通ルール(全ステップ共通)
- フィラー(「えー」「あの」等)・言い淀み・意味のない相槌を除去する
- 表記ゆれを統一し、口語を書き言葉に整える
- 入力に無い事実を推測・創作しない(ハルシネーション禁止)
- 判断できない箇所は削除せず「(要確認)」と明記する

# プロジェクト固有設定の扱い
PROJECT_CONFIG セクションの内容を、話者の名寄せ/トピック粒度/見出し構成の指示として使う

# 出力フォーマット
(Markdown の見出し構造を具体的に指定)

# 禁止事項
- 出力に前置き・後置きの説明文(「以下が結果です」等)を含めない
- コードブロックで全体を囲まない
- 入力の区切りヘッダを出力に含めない
```

**出力に前置きを含めない**指示は、`claude` の stdout をそのまま成果物ファイルにするため必須。

**出力の1行目の契約はスクリプト側の検証対象である**(2026-08-18 追加。[02-generate-minutes.md §5.5](./02-generate-minutes.md))。`generate_minutes.sh` は各ステップの出力の1行目を照合し、一致しなければ生成物を確定せず失敗させる(出力上限で `claude` が応答を自動継続し先頭が失われた出力を、成功扱いで確定させないため)。

| ステップ | スクリプトが要求する1行目 | プロンプト側の記述 |
|---|---|---|
| 1・2 | Markdown の見出し(`#`〜`######`)または箇条書き(`- `)で始まる | `出力の1行目は ## 会議情報 か …` の禁止事項 |
| 3 | `# ` で始まる | `出力の1行目を # 議事録: で始める` |

**判定は「構造」のみで、見出しの文言は見ない。** プロジェクトが `prompts/*.md` の見出し語や議事録タイトルを変更しても失敗しない。ただし**1行目を平文にする改変(前置きの説明文・コードブロック開始行など)はスクリプトに弾かれる**ため、プロンプトを改変する際はこの契約を崩さないこと。

ステップ別の出力フォーマット指定:

| ファイル | 出力構造 |
|---|---|
| `01_organize.md` | 先頭に**任意の `## 会議情報` ブロック**(日時 / 場所 / 出席者 / 議題。入力に記載がある項目のみ)。続けて `## <話者名>(<役職> / <会社>)` ではなく、時系列に `- **話者名**: 発言内容` を並べる。話者不明は `- **(不明)**:` とする |
| `02_structure.md` | `## 会議情報` ブロックが入力にあれば**先頭にそのまま引き継ぐ**。続けて `## トピック: <topic>` ごとに `### 論点` / `### やり取り`(質問→回答、提案→合意/保留を明示)/ `### 結論・持ち越し` |
| `03_format.md` | `config.yaml` の `minutes_sections` の順に `##` 見出しを立てる。ToDo は `| 担当 | 内容 | 期限 |` の表形式。`詳細な議事録(発言者・発言内容)` に相当するセクションがある場合のみ、その配下にトピックごとの `###` 見出しを立て、`- 発言内容(発言者名)` を起点+1段ネスト(応答)で並べる(§2.3) |

### 2.1 会議メタ情報の引き継ぎ(2026-08-17 の実機E2Eを受けた調整)

議事メモ冒頭の「日時 / 場所 / 出席者 / 議題」は発言ではないため、ステップ1が発言リストのみを出力すると失われ、`minutes_sections` の `会議概要` が常に `(要確認)` になる。これを避けるため、**ステップ1・2の出力先頭に任意の `## 会議情報` ブロックを許可**し、ステップ3がこれを `会議概要` の情報源として使う。

- 入力に記載が無い項目は行を書かない。ブロックごと無い場合は出力しない(**推測で補わない**)。
- ステップ3は、出席者を `PROJECT_CONFIG` の `speakers[]` から推定してはならない(`会議情報` に記載がある場合のみ列挙し、無ければ `(要確認)`)。`speakers[]` は表記統一と役職・会社の補足にのみ使う。
- ステップ1・2の「見出しを付けない」「1行目を `## トピック:` で始める」という制約は、この `## 会議情報` ブロックのみ例外とする。

### 2.2 `/minutes-review` の指摘を受けた調整(2026-08-17)

イテレーション5の成果物に `/minutes-review` を実行して検出した欠落・変質に対し、以下をプロンプト・`config.yaml` 側で対処した(スクリプトは変更しない)。

| 検出された問題 | 落ちた段 | 対処 |
|---|---|---|
| 要件・目標値・見積(「6時間 → 1時間以内」「並列化で2時間の見込み」「分割ありは+15人日」)が議事録に残らない | ステップ3(`minutes_sections[]` に置き場が無い) | `minutes_sections[]` の既定値に **`検討事項(要件・目標値・見積)`** を追加(`決定事項` の次)。併せて `03_format.md` に「検討中の要件・目標値・見積は決定でも ToDo でもないため該当セクションへ数値のまま残す」ルールを追加 |
| 受諾発言の無い `(依頼)` が `結論:` に格上げされ、議事録で決定事項として断定された | ステップ2 | `02_structure.md` に「`結論:` に書けるのは合意・決定・確定した変更のみ。`(依頼)` は受諾が無ければ `持ち越し:` に『依頼(受諾未確認)』として書く。`(報告)` された見積・現状値も `結論:` に書かない」を追加 |
| 決定事項に担当付きで書かれた作業(「テストデータ作成を試作 次郎に集約する」)が ToDo 表に無い | ステップ3 | `03_format.md` に「決定事項に担当が示された作業も ToDo に1行立てる(期限不明は `(要確認)`)」を追加 |

`minutes_sections[]` はプロジェクト固有設定であり(要件3.2.4、要件定義書2章は「決定事項/ToDo/懸念事項/次回アクション **等**」と例示に留める)、この追加は雛形の既定値の変更にあたる。プロジェクト側で不要であれば `config.yaml` から削除してよい。

### 2.3 `詳細な議事録(発言者・発言内容)` セクション(2026-08-17 / 実プロジェクト `projects/{project-name}`)

トピック単位に発言そのものを残したいプロジェクトのために、`minutes_sections[]` に `詳細な議事録(発言者・発言内容)` を追加できるようにした。**プロジェクト固有の任意セクション**であり、`_template` / `sample` の既定値には含めない(発言の列挙が不要なプロジェクトでは既定の挙動を変えないため)。

| 項目 | 決定 | 理由 |
|---|---|---|
| 書式の置き場 | 見出し名は `config.yaml` の `minutes_sections[]`、書き方(トピック `###` 見出し・ネスト・発言者表記・`# 宿題事項`)は `prompts/03_format.md` の独立した節 | 「どの見出しを立てるか」=プロジェクト設定、「どう書くか」=プロンプトという §1/§2 の分担を維持する(`CLAUDE.md` 3章) |
| `minutes_sections[]` の書式 | **見出し名のみのフラットな list of string を維持し、項目配下にネストした箇条書きを書かない** | 2026-08-17 実測:`- 見出し名` の下に字下げした箇条書きを書くと YAML では1本の長い plain scalar に連結される(`"詳細な議事録(...) - トピック単位で整理する - ..."`)。シェルはパースしないため実害は出ないが、§1 のスキーマ(list of string)から外れ、他ツールでの再利用時に壊れる |
| 発言の書式 | `- 発言内容(発言者名)` をトップレベル(起点の発言)、応答を1段ネスト。ネストは2段まで | ステップ2の `### やり取り` の応答関係をそのまま写せる最小の構造。3段以上は読みにくく、`(質問)`/`(回答)` の役割表記も不要になる |
| 宿題事項の印 | 由来となった発言の行末に ` # 宿題事項` を付け、**ToDo 表の行と対応させる** | 議事録内で ToDo とその発言根拠を相互に辿れるようにする。片側にしか現れない状態はステップ3の抜けとして検出できる |
| 既存ルールとの整合 | 「議論の経過(誰が何を言ったかの列挙)は議事録に含めない」を「詳細な議事録に相当するセクションにのみ書く / 当該セクションが無ければ含めない」に緩和。禁止事項の「`minutes_sections[]` に無い見出しを追加しない」は当該セクション配下の `###` を例外とする | この2つのルールは新セクションと正面衝突するため、条件付きに書き換えないとステップ3の指示が矛盾する |

要件定義書2章は議事録の構成を「決定事項/ToDo/懸念事項/次回アクション **等**」と例示に留めているため、この追加による要件定義書の変更は不要。

### 2.4 分割実行時のラベル契約(要件3.2.8 / 2026-08-18)

`--parallel N` でステップ1・2を分割実行する場合、stdin に3つのラベルが追加される([02-generate-minutes.md §9.2](./02-generate-minutes.md))。**連結時の重複除去をスクリプト側で実装しない**方針([09-decisions.md §5.2](./09-decisions.md))のため、パート出力を単純結合できる状態はプロンプトの遵守によって担保される。よって以下を `01_organize.md` / `02_structure.md` に明記する。

| ラベル | プロンプト側の扱い |
|---|---|
| `PART_INFO` | `part: i/N` の1行。**`i` が 1 のときのみ `## 会議情報` ブロックを出力する。** 2 以降のパートは会議情報を出力しない(§2.1 の会議情報は会議に1つであり、パートごとに繰り返すと連結後に重複する) |
| `CONTEXT_BEFORE` | 直前パート末尾の重なり。**文脈把握にのみ使い、出力に含めない** |
| `CONTEXT_AFTER` | 次パート先頭の重なり。同上 |

- 分割対象の本体セクションは従来と同じラベル(`TRANSCRIPT` / `MEETING_MEMO`、ステップ2は `STEP1_OUTPUT`)で渡り、ファイル名表示に ` part i/N` が付く。**プロンプトはラベルの意味を変えずに済む**(パート実行専用の分岐を増やさない)。
- 上記3ラベルは**単発実行では現れない**。プロンプトには「これらのセクションが存在する場合のみ適用する」条件付きの指示として書き、単発実行時の挙動を変えない。
- `CONTEXT_*` の指示が守られなかった場合(重なりが出力に混入した場合)の検知は `/minutes-review` の重複指摘に委ねる。スクリプト側の後処理では検知しない。

ステップ固有の追加指示:

- `01_organize.md`:担当範囲が話題の途中から始まる・途中で終わる場合も、**その範囲を切り出したまま出力する**(前後を補完せず `(要確認)` も付けない。分割は機械的なものであり、会議側の不明点ではない)。
- `02_structure.md`:担当範囲がトピックの途中から始まる場合も**そのトピックの `##` 見出しを付けて出力する**(見出しの無い本文を作らない)。担当範囲内で結論が出ていなければ `結論: なし(継続議論)` とし、他パートに結論があると推測しない。

`03_format.md` には、チャンク境界での分断の受け皿として次を追加する。ステップ3は連結後の単発実行であり、分割を意識しないためラベルの追加は無い。**分断されたトピックを統合できるのは会議全体を1回で読むステップ3だけ**なので、統合責務はここに置く。

- **同名・同主旨のトピックが複数回現れる場合は1つに統合する。**
- 前半のパートが `結論: なし(継続議論)` でも、後半の同じトピックに結論があればそちらを採る。
- 重複する決定事項・ToDo・懸念事項は1行にまとめる(食い違う場合は両方残して `(要確認)`)。
- 連結の痕跡(`## 会議情報` の重複、同名トピックの繰り返し)を議事録に持ち込まない。

`projects/_template/prompts/` を正として `projects/sample/` および実プロジェクト `projects/{project-name}/` へ反映する。`sample` はテンプレートとの差分が今回の追加のみだったためファイルごとコピーしたが、**実プロジェクトが独自構成(`詳細な議事録` セクション等・§2.3)を持つ場合はコピーせず該当箇所のみ個別に編集する**(実プロジェクトの `03_format.md` では `詳細な議事録` 配下のトピック `###` 見出しも重複させない指示を併せて追加した)。

## 3. `.claude/commands/minutes-review.md` 設計(要件3.3)

- 引数:`<project> <date>`。**`$ARGUMENTS` を空白区切りで解釈する形で受け取る**(2026-08-17 実測:位置引数 `$1` / `$2` は呼び出し経路によって番号がずれる・展開されないことがあり、`$1` に日付が入る事象を確認したため、本コマンドでは位置引数を使わない)。ファイルパスは `{project}` / `{date}` のプレースホルダで記述し、コマンド本文冒頭で読み替えを指示する。
- フロントマター:`description`(コマンド一覧での説明)、`argument-hint`(`<project> <date>`)、`allowed-tools`(`Read` / `Glob` / `Grep` / `Write`)。
  - `Edit` / `MultiEdit` / `Bash` は与えない。**既存ファイルの部分改変ができないため、`minutes.md` を書き換えて「直したことにする」経路が閉じている**(要件3.3の「指摘のみ」)。`Write` はレビュー結果の新規保存(§3.1)のためだけに許可する。
- 引数が不足している場合・参照ファイルが1つも無い場合は、レビューを行わず不足内容と次の操作(`./scripts/generate_minutes.sh <project> <date>` の実行)を提示して終了する。
- 参照ファイル(存在するものすべて):
  `inputs/{p}/{d}/` 直下の `*.md` / `*.txt`(**議事メモは複数存在しうるため Glob で列挙して全件読む**。固定名 `memo.md` に依存しない)、`outputs/{p}/{d}/00_transcript.txt`、`01_speakers_utterances.md`、`02_structured_conversation.md`、`minutes.md`。
- 複数インプット([02-generate-minutes.md §4.2・§6](./02-generate-minutes.md))に対応して、追跡観点に次を含める:一方のメモにしか無い項目の欠落、メモ間の食い違いが片方に確定されていないか、文字起こしの後半パートの議題が落ちていないか。
- 本コマンドは**対話モードで実行される**ため `CLAUDE.md` が適用される。ファイル読み込みは Read ツールで行う(運用パイプラインとは異なり `--tools ""` の制約は無い)。
- 出力フォーマット:
  ```markdown
  ## 1. 議事録から漏れている内容
  - <内容> (根拠: 00_transcript.txt の該当発言 / 01→02 のどこで落ちたか)
  ## 2. 矛盾点
  - <箇所A> と <箇所B> が矛盾
  ## 3. 要確認・フォローアップ事項
  - <項目>(誰に何を確認すべきか)
  ```
- 各指摘には**中間生成物のどの段で情報が落ちた/変質したか**を併記させる(要件3.3の「追跡」)。
- 議事録ファイルの自動修正は行わない(指摘のみ)。修正は利用者の判断で該当ステップを再実行する。

### 3.1 レビュー結果の保存(要件3.3)

指摘は画面に表示するだけでなく、**`outputs/{project}/{date}/review_{NN}.md` に保存する**。会話履歴を遡らずに再実行の作業リストとして使えるようにし、プロンプト調整の前後比較を可能にするため。

| 項目 | 決定 | 理由 |
|---|---|---|
| 保存先 | `outputs/{project}/{date}/`(★Git管理外) | レビュー結果は会議内容そのものを含むため、パイプラインの成果物と同じ機密扱いにする(要件6.2)。専用ディレクトリを増やさない |
| ファイル名 | `review_01.md` から始まる**2桁連番** | 既存を上書きせず、`--only-step N` の再実行前後を比較できる |
| 連番の決定 | `Glob` で `outputs/{project}/{date}/review_*.md` を列挙し、最大値 +1(1件も無ければ `01`) | `Bash` を与えずに実現できる。`Write` は**新規パスへの書き込みのみ**になる |
| ファイル内容 | 先頭に対象(`project` / `date` / レビュー実施日 / 参照したファイル一覧)、続けて画面出力と同じ3節 + 再実行の提案 | 単体で読んで文脈が分かるようにする |

- **既存の `review_{NN}.md` を上書きしてはならない**(`Glob` の結果に含まれるファイル名を再利用しない)。
- 保存できなかった場合(権限が拒否された等)は、画面への指摘出力だけは必ず完了させる。レビュー結果を失わないことを保存より優先する。
- `outputs/` 配下は `.gitignore` 済みであり、レビュー結果ファイルについて追加のパターン設定は不要([06-security.md §1](./06-security.md))。
- パイプラインの成果物は一時ファイル(`mktemp`)経由で作られるため `0600` になるが、レビュー結果ファイルは Write ツールが作るため**プロセスの umask に従う**(2026-08-17 実測:`0666 & ~umask`)。Git への漏洩経路は無く、`Bash` を与えずに `chmod` する手段も無いため、パーミッションの統一は行わない(ローカルの共有環境で厳格化が必要になった場合のみ再検討する)。
