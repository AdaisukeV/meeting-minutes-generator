# 議事録生成アプリ 要件定義書

## 1. 概要

Claude Code(CLI)を利用して、会議の議事メモおよび会議録画から議事録(Markdown形式)を自動生成するローカル実行アプリケーション。
プロジェクト(取引先/案件)ごとに話者・会社名・議事録構成をカスタマイズ可能とし、生成後は専用スラッシュコマンドでレビュー(抜け漏れ・矛盾点の指摘)を行える。

会議には機密情報が含まれるため、外部への情報漏洩防止を最重要要件とする。

---

## 2. インプット / アウトプット

### インプット
- 議事メモ(Markdown / テキスト)
  - Google MeetでGeminiが自動生成したメモ
  - 人間が作成したメモ
- 会議録画(音声・動画ファイル)

**1回の会議に対して、議事メモ・録画のいずれも複数ファイルを配置できる。**

- 議事メモ:同一会議に対してGeminiメモと人間メモの両方が存在するケースを想定する。`inputs/{project}/{date}/` 直下の `*.md` / `*.txt` を**すべて**インプットとして扱い、1件も無視しない。
- 会議録画:会議を中断して録画を再開した場合、1つの会議が複数ファイルに分割される。この場合も全ファイルを文字起こしし、**ファイル名の昇順**で連結して1つの会議の記録として扱う(詳細は3.1)。

### アウトプット
- Markdown形式の議事録ファイル

---

## 3. 機能要件

### 3.1 音声・動画の前処理(文字起こし)
- Claude Codeは音声・動画を直接処理できないため、**ローカル環境で文字起こしを実施してからテキストとしてClaude Codeに渡す**。
- 文字起こしツールは `faster-whisper` を採用(ローカルCPU/GPUで完結、外部送信なし)。
- 出力はプレーンテキスト(タイムスタンプ付き推奨)とし、議事メモと同様に議事録生成の入力として扱う。出力先は `outputs/{project}/{date}/00_transcript.txt` とする。
- 文字起こしは**議事録生成パイプラインのステップ0**として位置づけ、`generate_minutes.sh` が(3.2のステップ1に先立って)`transcribe.py` を自動的に呼び出す。利用者が文字起こしを個別に実行する必要はない。
  - `00_transcript.txt` が既に存在する場合は**再実行せずスキップ**する(文字起こしは処理時間が長いため。再作成したい場合は当該ファイルを削除する運用とする)。
  - 録画・音声が無く議事メモのみの会議では、文字起こしをスキップしてステップ1へ進む。
  - ステップ1を実行しない再実行(3.2.5の途中ステップ指定)では、文字起こしは実行しない。
- **録画・音声が複数ファイルある場合(会議の中断・再開による分割)は、全ファイルを文字起こしして連結する。**
  - 連結順は**ファイル名の昇順**とする。この順序が会議の時系列順であることを前提とするため、連結順を実行時に表示し、利用者が確認できるようにする。順序を制御したい場合はファイル名に連番を付ける運用とする。
  - 文字起こし結果は**メディア1本ごとに `outputs/{project}/{date}/00_transcript_parts/` へ保存**し、`00_transcript.txt` はそれらを連結して生成する。録画を後から追加した場合、既存分の文字起こしをやり直さずに済ませるため(処理時間が長いため)。
  - 各ファイルのタイムスタンプは先頭から振り直されるが、**累積オフセットの加算は行わない**。会議を中断しているため実時間に空白があり、加算すると存在しない時刻を作ってしまう。代わりに連結箇所へ区切りを挿入し、時系列は出現順で表す。

### 3.2 議事録生成プロセス(3段階パイプライン)

議事メモ・文字起こしから一度に議事録を生成するのではなく、以下の3段階に分解して処理する。各段階の出力は中間生成物としてファイルに永続化し、人間による確認・手直しや `/minutes-review` からの参照を可能にする。

#### 3.2.1 ステップ1:話者・発言の整理
- 議事メモ(Geminiメモ/人間メモ)と文字起こし結果を統合し、「話者+発言内容」の粒度に整理する。
- **議事メモが複数ある場合は全件を入力として渡す。** すべてを相補的な情報として扱い、どちらかを捨てない。記述が食い違う場合は3.2.4のハルシネーション防止方針に従い、どちらかを採用せず `(要確認)` を付けて残す。
- 話者の特定・名寄せには、プロジェクト固有設定(話者名・役職・所属会社名のマッピング)を用いる。
- 出力:`01_speakers_utterances.md`

#### 3.2.2 ステップ2:会話の構造化
- ステップ1の出力を、トピック単位・応答関係(質問→回答、提案→合意/保留 等)で構造化する。
- 出力:`02_structured_conversation.md`

#### 3.2.3 ステップ3:議事録フォーマット
- ステップ2の構造化結果を、プロジェクト固有の議事録構成(決定事項/ToDo/懸念事項/次回アクション 等)に整形する。
- 出力:`minutes.md`(最終アウトプット)

#### 3.2.4 各ステップ共通のシステムプロンプト設計
- **共通ルール(全プロジェクト共通、全ステップ共通)**
  - フィラー(「えー」「あの」等)、言い淀み、意味のない相槌などの除去
  - 表記ゆれの統一、口語→書き言葉への整形
  - 事実に基づかない推測・創作の禁止(ハルシネーション防止)
- **プロジェクト固有設定(プロジェクトごとに変更可能、ステップごとにファイル分割)**
  - ステップ1用:話者名・役職・所属会社名のマッピング
  - ステップ2用:トピック分類の粒度・観点(必要に応じて案件ごとに調整)
  - ステップ3用:議事録の見出し構成、文体・敬体/常体などのスタイル指定
- 実装方針:`system_prompt.md` を単一ファイルにせず、`projects/{name}/prompts/01_organize.md` / `02_structure.md` / `03_format.md` にステップ単位で分割する。

#### 3.2.6 中間生成物のフォーマット(Markdown採用の理由)
中間生成物(`01_speakers_utterances.md`・`02_structured_conversation.md`)はJSON等の厳密な構造化形式ではなく、**Markdownで出力する**方針とする。理由は以下の通り。

- 人間が中間生成物を直接確認・手直しする運用を想定しており、Markdownの方が非エンジニアにも編集しやすい
- 各ステップの読み手(次ステップの入力)はClaude Code自身であり、LLMの解釈に強い自然言語+軽構造(Markdown)の方が、厳密なJSONスキーマを崩さず生成させ続けるより安全
- `/minutes-review`もLLMが読む前提であり、プログラム側でのパース・機械的な差分比較は現時点でスコープ外
- 将来、機械的な集計・分析等でスキーマ的な構造化データが必要になった場合は、Markdown内にYAML Front Matter等で軽量な構造化情報を併記する形で拡張可能(8章「今後の検討事項」参照)

#### 3.2.5 Claude Codeの呼び出し方針
- 3ステップは**独立した呼び出し**とし、各ステップの出力を次ステップの入力として明示的に固定する(1セッション内で暗黙に進めさせない)。
- これにより、特定ステップ(例:ステップ2の構造化のみ)の再実行・修正が、他ステップへ影響を与えずに行える。
- `generate_minutes.sh` はステップごとに関数化し、`--from-step 2` のように途中ステップからの再実行を指定できるようにする(将来拡張含む)。あわせて、1ステップのみを実行する `--only-step N`(N=0はステップ0の文字起こしのみ)、実際には生成を行わず実行計画のみを表示する `--dry-run`、ステップ1・2を分割して並列実行する `--parallel N`(3.2.8)を用意する。
- **1ステップの実行は数分〜数十分に達するため、実行中の経過を定期的に表示する**(生成物の標準出力はファイルへリダイレクトされるため、無表示のままでは「処理中」と「停止」を利用者が区別できない)。あわせて `Ctrl+C` による中断は**処理の失敗と区別して報告**し、認証・入力サイズの見直しを促す HINT を出さない。
- 各ステップの呼び出しは非対話モード(`claude -p`)で行い、**`--system-prompt-file` オプションでシステムプロンプトを完全に置き換える**(`projects/{name}/prompts/01_organize.md` 等を指定)。`CLAUDE.md`とプロジェクト固有プロンプトの役割分担は3.2.7を参照。
- ただし、**`--system-prompt-file` だけではリポジトリ直下の `CLAUDE.md` の混入を防げない**(`CLAUDE.md` の自動読み込みはシステムプロンプトとは別経路で行われるため)。実機検証で混入が確認されたため、運用時の呼び出しでは以下を併用する(二重防御)。
  - `--bare` を指定して `CLAUDE.md` の自動読み込み・自動メモリ・hooks・plugin を無効化する。
  - リポジトリ外の空ディレクトリをカレントディレクトリとして実行し、親ディレクトリを遡って `CLAUDE.md` が発見されることを構造的に防ぐ。
  - なお `--bare` の併用により、Anthropic への直接認証は `ANTHROPIC_API_KEY`(または `apiKeyHelper`)に限定され、コンシューマープランのOAuthログインは利用できない。本アプリはBedrockまたは商用APIキーを前提とし、コンシューマープランは非推奨(6章4項)であるため支障はない。
- **生成結果は、各ステップのプロンプトが定める「出力の1行目」の契約を満たすことを検証し、満たさない場合は失敗として停止する**(中間生成物・議事録を確定しない)。1回の応答が出力トークン上限に達すると Claude Code が応答を自動継続し、**非対話モードでは最後の応答だけが返るため、それ以前に生成された内容が失われた出力が「成功(終了コード0)」として確定してしまう**(実測。`docs/design/09-decisions.md` 6.5)。終了コード・空出力の判定では検知できないため、この検証を独立した完了条件として設ける。
- 各ステップの入力(プロジェクト固有設定・議事メモ・文字起こし・前段の中間生成物)は**スクリプトが連結して標準入力(stdin)経由で渡し**、生成結果は標準出力(stdout)を受け取ってスクリプト側がファイルへ書き込む。あわせて **`--tools ""` で全ツールを無効化**し、Claude Code側にファイルアクセス・ネットワークアクセスを与えない(6章のセキュリティ要件と整合させるため)。

#### 3.2.7 `CLAUDE.md`(開発時)と運用時プロンプトの役割分担
本アプリの開発と運用では、Claude Codeに求める役割が異なるため、システムプロンプトを明確に分離する。

| | 対象 | 適用範囲 | 内容 |
|---|---|---|---|
| `CLAUDE.md`(リポジトリ直下) | **開発時**。対話モードでアプリのコードを書く・直すとき | 開発者がClaude Codeと対話するセッション | コーディング規約、アーキテクチャ制約、セキュリティ上守るべきルール等 |
| `projects/{name}/prompts/01_organize.md` 等 | **運用時**。`generate_minutes.sh`から`-p`(非対話)実行するとき | 議事録生成パイプラインの各ステップ呼び出し | 話者整理・構造化・フォーマットの指示(3.2.1〜3.2.3) |

- 運用時の呼び出しでは、`--system-prompt-file` によるシステムプロンプトの完全置き換えに加えて **`--bare` の指定とリポジトリ外の空ディレクトリでの実行**を併用することで、`CLAUDE.md`の開発者向けルールが議事録生成処理に適用されない構成とする(3.2.5参照)。
  - **`--system-prompt-file` 単独ではこの分離は成立しない。** システムプロンプトを置き換えても `CLAUDE.md` は別経路(プロジェクトメモリの自動読み込み)で参照されるため、実機検証では `CLAUDE.md` の記述内容が原文のまま引用できる状態だった。この分離要件を変更・簡略化する場合は、必ず実機で混入の有無を再検証する。
- 開発フェーズで `generate_minutes.sh` の初回動作確認を行う際は、`CLAUDE.md`の内容が意図せず出力に影響していないかを確認する。

#### 3.2.8 長大な入力の分割と並列実行

長時間会議では、ステップ1・2の1回の呼び出しが数十分に達する。**所要時間の律速は入力サイズではなく出力トークンの逐次生成**であり、ステップ1は全発言を1行ずつ書き直し、ステップ2は `やり取り` として全発言を役割付きで再掲するため、いずれも出力が数万トークン規模になる。したがって**分割を直列で実行しても所要時間は短縮しない**(生成する総トークン量が変わらず、各チャンクへ議事メモを再添付する分だけ入力が増える)。短縮は分割したチャンクを**並列実行**して初めて得られる。

- ステップ1・2は入力をチャンクへ分割し、**チャンク単位で並列実行できる**ようにする。`--parallel N` で指定し、既定は 1(分割・並列を行わず単発実行する従来動作)とする。
  - 並列度の既定を 1 とするのは、Bedrock 側のスロットリングを避けるため。並列実行は利用者による**明示的なオプト・イン**とする。
  - ステップ3は構造化結果から議事録への凝縮であり出力が小さいため、**チャンクを連結した後に単発で実行**する。
- **分割対象は1ファイルに限定し、ステップごとに独立して決める。** ステップ1は `00_transcript.txt` があればそれ、無い場合は議事メモのうち最大バイト数のもの。ステップ2はステップ1の中間生成物(唯一の入力)。ステップ1のパート境界をステップ2に引き継がないのは、`--from-step 2` のような部分再実行(3.2.5)でも分割できるようにするため。
  - **議事メモは分割しない。** 話者の名寄せ・固有名詞の確認に全チャンクで必要となるため、分割対象以外の議事メモは全チャンクへ全文を添付する。
  - 分割対象として選ばれたファイル名とパート数は実行時に表示し、利用者が確認できるようにする(3.1 の連結順表示と同じ理由。規則を明示し実行時に検証可能にする)。
- **分割は行数ベースで行い、チャンク境界の前後にオーバーラップ(重なり)を持たせる。** 境界付近の話者推定・応答関係の手がかりが失われるのを防ぐため。
  - 重なり部分は本体と**別のラベル**で渡し、**出力に含めてはならない範囲**であることをプロンプト側で明示する。連結時の重複除去処理は実装しない(機械的な重複判定は表記の揺れに弱く、発言の取り違え・欠落を招くため)。
  - 各チャンクには**通し番号と総パート数**を渡し、会議のメタ情報ブロック(`会議情報`)を先頭パートのみが出力するよう制御する。
- チャンクごとの出力は `outputs/{project}/{date}/01_parts/`・`02_parts/` へ保存し、**既存パートがあれば再実行しない**(3.1 の `00_transcript_parts/` と同じ理由。一部のパートだけを作り直せるようにするため)。確定した中間生成物はパートを連結して生成する。
- 1つでもパートが失敗した場合は、**全パートの完了を待ってからエラーとして停止**し、中間生成物を確定しない(一部のパートのみが反映された中途半端な出力を残さないため)。

### 3.3 議事録レビュー(カスタムスラッシュコマンド)
- `/minutes-review` コマンドを実装。
- 生成済みの議事録(`minutes.md`)、および中間生成物(`01_speakers_utterances.md`・`02_structured_conversation.md`)と、元インプット(議事メモ+文字起こし)を突き合わせ、以下を指摘する。
  - インプットに含まれる情報のうち議事録から漏れている内容
  - インプット間・議事録間の矛盾点
  - 要確認・要フォローアップ事項
- 中間生成物を参照することで、「どの発言がどのトピックに集約され、最終的にどう反映されたか」を追跡し、抜け漏れ・矛盾の指摘根拠を明確にする。
- 指摘結果は画面に表示するとともに、`outputs/{project-name}/{date}/review_{NN}.md`(★Git管理外)へ Markdown で保存する。既存のレビュー結果は上書きせず連番を繰り上げ、部分再実行(`--only-step N`)前後の指摘を比較できるようにする。
- 本コマンドは**指摘のみを行い、議事録ファイルを修正しない**。修正は利用者が該当ステップを再実行して行う。

### 3.4 認証経路の抽象化(利用環境の柔軟な切替)
将来的に部門で商用アカウント(Anthropic API等)を契約する可能性があるため、**認証設定と議事録生成ロジックを分離**する。

- 対応予定の認証経路
  - Amazon Bedrock(現時点の第一候補。個人情報保護の観点から採用)
  - Anthropic 商用APIキー(将来の部門契約時)
  - (将来検討)Google Vertex AI 等、他クラウド経由
- 実装方針
  - `config/auth/*.env.example` に経路ごとのテンプレートを用意
  - 利用者は該当テンプレートを `config/auth/active.env`(Git管理外)にコピーして値を設定
  - 実行スクリプトは `active.env` を読み込むのみで、認証経路による分岐ロジックを持たない
  - Bedrock利用時はモデルIDを明示的に固定(バージョン自動追従による破壊的変更を防止)
  - **モデルIDはステップ別に上書きできる。** ステップ1はフィラー除去・表記統一・話者の名寄せという機械的な処理が主であり、判断の重さはステップ2・3にあるため、ステップ1のみ軽量なモデルへ振れると所要時間を短縮できる。`ANTHROPIC_MODEL_STEP1` / `_STEP2` / `_STEP3` を任意設定とし、未設定のステップは `ANTHROPIC_MODEL` にフォールバックする。エイリアス(`sonnet` 等)を使わずモデルIDを明示する方針、および認証経路による分岐を持たない方針は維持する。

#### 3.4.1 Amazon Bedrock利用時のSSO認証

静的なアクセスキーをローカル・リポジトリに保存しないため、Bedrock経由の認証は **AWS SSOログイン方式** を採用する。

- `scripts/aws_sso_login.sh` を用意し、以下を行う。
  - `config/auth/active.env` から `AWS_PROFILE` を読み込む
  - `aws sts get-caller-identity` で既存SSOセッションの有効性を確認し、**有効な場合は再ログインをスキップ**する(実行のたびにブラウザ確認が発生しないようにするため)
  - セッションが無効な場合のみ `aws sso login --profile "$AWS_PROFILE"` を実行する
- `generate_minutes.sh` は、`active.env` 内に `CLAUDE_CODE_USE_BEDROCK=1` が設定されている場合のみ、処理開始前に `aws_sso_login.sh` を自動的に呼び出す。
  - 商用APIキー等、他の認証経路に切り替えた場合はこのSSOログイン処理自体がスキップされ、認証経路を柔軟に切り替えるという要件(3.4)と矛盾しない構成とする。
- 前提として、利用者は初回のみ `aws configure sso --profile <profile名>` でSSOプロファイルを作成しておく必要がある。
- Codespaces(ヘッダレス環境)上でも、認証用URL・コードがターミナルに表示される形で動作するため問題なく利用できる。ただし初回はローカルPCのブラウザで当該URLを開いて認証する必要がある旨を利用者に案内する。

## 5. 実行フロー(利用イメージ)

```bash

# → config.yaml / prompts/01_organize.md / 02_structure.md / 03_format.md を編集
#   (会社名・話者・トピック観点・議事録構成)

# インプットを配置
# inputs/client-a/2026-08-16/ に議事メモ(.md / .txt)と録画を配置
#   議事メモは複数可(例:gemini_memo.md と human_memo.txt の両方)
#   録画も複数可(中断・再開で分割された場合。ファイル名の昇順で連結される)

# 議事録を生成(ステップ0→1→2→3を順次実行、Bedrock利用時はSSOセッションを自動チェック)
./scripts/generate_minutes.sh client-a 2026-08-16
# → outputs/client-a/2026-08-16/ に
#     00_transcript_parts/(メディア1本ごとの文字起こし。再実行時に再利用)
#     00_transcript.txt(パートを連結したもの。既存ならスキップ、録画が無ければ省略)
#     01_parts/ ・ 02_parts/(--parallel 指定時のみ。チャンクごとの出力。再実行時に再利用)
#     01_speakers_utterances.md(話者・発言整理)
#     02_structured_conversation.md(構造化結果)
#     minutes.md(最終アウトプット)
#   が順次生成される

# 長時間会議でステップ1・2を分割して並列実行(既定は 1 = 従来の単発実行)
# ./scripts/generate_minutes.sh client-a 2026-08-16 --parallel 4

# 途中ステップの内容に問題があれば、そこだけ修正して再実行も可能
# 指定ステップから最終ステップ(3)まで再実行
# ./scripts/generate_minutes.sh client-a 2026-08-16 --from-step 2

# 指定ステップのみ再実行(0 は文字起こしのみ)
# ./scripts/generate_minutes.sh client-a 2026-08-16 --only-step 2

# 実行計画のみ確認(生成は行わない)
# ./scripts/generate_minutes.sh client-a 2026-08-16 --dry-run

# Claude Code上で議事録レビューを実施(中間生成物も参照)
/minutes-review client-a 2026-08-16
```

## 6. セキュリティ要件

1. **音声・動画の生データは外部送信しない**。文字起こしはローカル(faster-whisper)で完結させる。
2. **`inputs/`・`outputs/`・`projects/{project-name}/`(雛形 `_template` と動作確認用 `sample` を除く)・`config/auth/active.env` は Git 管理対象外**とし、GitHubリポジトリには機密データ・認証情報を一切含めない。リポジトリにはコード・テンプレート・設定の雛形のみを含める。プロジェクト固有設定は話者の名寄せのために実在の顧客名・個人名を書く前提(3.2.4)であるため、除外を既定とし雛形側を例外として復帰させる。
3. **利用経路(Bedrock / 商用API等)は用途に応じて選定**。現時点ではAmazon Bedrock経由を優先し、AWSの管理境界内で処理を完結させる。将来商用API契約に切り替える場合も、認証テンプレートの追加のみで対応可能な構成とする。
4. 個人アカウント(Pro/Max等のコンシューマープラン)での運用は、学習利用・データ保持期間の観点から**本アプリでは非推奨**とする。
5. **Bedrock利用時は静的なAWSアクセスキーを保存せず、AWS SSOログイン方式を採用**する(3.4.1参照)。認証情報はローカルのSSOセッションキャッシュにのみ保持され、リポジトリ・`active.env`のいずれにも長期的な認証情報を書き込まない。
6. **Codespaces上のAWS認証情報はリポジトリ/Organizationの Codespaces Secrets で管理**し、`devcontainer.json`経由でコンテナに引き渡す(7章参照)。`active.env`にはプロファイル名やリージョンなど非機密の設定値のみを記載する運用を基本とする。

## 7. 開発環境に関する補足(AI駆動開発向け)

- 開発環境:GitHub Codespaces / ローカル環境のいずれでも動作すること(環境依存の設定はすべて `config/` 配下に分離)
- Codespaces上でも `faster-whisper` 等の依存パッケージがインストール可能なことを前提とする(`requirements.txt` 等で明示)
- 認証情報(AWS認証情報・APIキー等)はCodespacesのSecrets機能、もしくはローカルの `active.env` で管理し、リポジトリには含めない

### 7.1 `.devcontainer/devcontainer.json` の要件

- ベースイメージ:`mcr.microsoft.com/devcontainers/base:ubuntu-24.04`
- 導入するFeatures
  - Node.js(Claude Code CLIの実行に必要)
  - Python 3.12以上(`faster-whisper`等の実行に必要。上限は固定しない)
  - AWS CLI(Bedrock利用時のSSO認証・IAM操作に必要)
  - GitHub CLI(リポジトリ操作の補助)
- `postCreateCommand` で以下を自動実行する(`postCreate.sh`に集約)
  - `ffmpeg` のインストール(音声・動画読み込みに必須)
  - Claude Code CLI のグローバルインストール
  - `requirements.txt` に基づくPython依存関係のインストール
- AWS認証情報は **Codespaces Secrets**(リポジトリまたはOrganization単位で事前登録)から `remoteEnv` を介してコンテナへ引き渡す。`devcontainer.json`・リポジトリ本体には認証情報を一切含めない。
- マシンスペック:文字起こし処理はCPU負荷が高いため、`hostRequirements`で最低4 CPU程度を指定することを推奨する(GPUは前提としない)。

### 7.2 Codespaces環境特有の考慮事項

- `faster-whisper` はCPU動作を前提とし、モデルサイズ(`base`/`small`/`medium`等)を `transcribe.py` の引数で選択可能にする。
- Bedrock SSOログイン(3.4.1)はヘッダレス環境でも認証用URL・コードの表示という形で動作するが、初回認証はローカルPCのブラウザで行う必要がある旨をREADMEに明記する。
- ローカル環境用の `config/auth/active.env` 方式と、Codespaces用の Secrets 経由の環境変数方式の両方に対応できるよう、`generate_minutes.sh` は「`active.env` が存在すればそれを読み込み、存在しなければ既存の環境変数をそのまま利用する」というフォールバック仕様とする。

### 7.3 ローカル環境(Codespaces 以外)でのセットアップ

7章冒頭の「Codespaces / ローカル環境のいずれでも動作すること」を満たすため、devcontainer が自動で行う導入(7.1)に相当する手順を、ローカル環境の利用者向けにREADMEへ明記する。

- 対象環境:macOS / Ubuntu・Debian / Windows(WSL2上のUbuntu)の3つとし、OS別の導入手順を併記する。Windowsネイティブ環境は対象外とする(パイプラインがBashスクリプト前提のため)。
- 導入対象:Python 3.12以上、`ffmpeg`、Node.js(Claude Code CLIの実行に必要なバージョン以上)、`requirements.txt` のPython依存。GPUは前提としない。
- 認証経路により追加で必要となるCLIを区別して示す:Amazon Bedrockは AWS CLI、Vertex AIは gcloud、Anthropic商用APIキーは追加CLI不要。
- Python依存は、OSのPython環境を変更しない方法(仮想環境)で導入できる手順を示す(`pip install --break-system-packages` を前提にしない)。
- OSのパッケージマネージャで必要なバージョンが得られない場合は、公式の配布物・インストーラを用いる手順を示す。
- WSL2では、ブラウザ認証をWindows側ブラウザで行う場合の扱い(7.2のヘッドレス環境と同じ)と、リポジトリ・入力ファイルの配置に関する注意を明記する。

## 8. 開発プロセス(設計書・TDD)

本アプリの開発は、以下の3段階で進める。

```
docs/requirements.md(本要件定義書)
   ↓
docs/design.md(設計書ハブ)+ docs/design/(分冊)
   ↓
実装(TDD)
```

- `docs/requirements.md`:**何を作るか(WHAT)**。本ドキュメント。
- 設計書:**どう作るか(HOW)**。各スクリプトの関数/コマンド単位のインターフェース(引数・返り値・標準出力/標準エラー・終了コード)、ステップ間のデータ受け渡し形式、`config.yaml`・`prompts/*.md`の具体スキーマ、エラーハンドリング方針、テスト戦略を記載する。分量が大きいため、以下の2階層で構成する。
  - `docs/design.md`(ハブ):位置づけ・全体アーキテクチャとデータフロー・ファイル構成・分冊索引・要件定義書との対応表。
  - `docs/design/*.md`(分冊):成果物単位の詳細設計(共通規約 / `generate_minutes.sh` / `transcribe.py` / 認証 / プロジェクト資産 / セキュリティ / テスト / 開発環境 / 設計判断の記録)。節番号は分冊ごとに独立させる。
  - 同じ内容をハブと分冊の両方に書かず、正は常に1箇所とする。実装時はハブの分冊索引から必要な分冊のみを参照する。
- 実装が要件定義書・設計書と乖離した場合は、コードを合わせるのではなく、まず設計書(該当する分冊)を実態に合わせて更新してから実装を進める。

### 8.1 開発時の運用ルール

- **セキュリティを最優先**とし、低下の恐れがある変更は作業を止めて合意を得てから進める。
- **KISS原則**に従い、過剰な抽象化を避ける。
- タスクは**最長30分程度の単位**に分割して進める。
- 以下の変更を行った場合は必ず `docs/memo/` に記録する。
  - コメントアウト
  - 処理削除
  - ライブラリ(依存パッケージ)の変更
- 依存パッケージの追加は最小限にし、追加時は標準機能・既存依存で代替できないかを先に検討する。
- 実行コマンドはCI/CD用のもの(非対話・非ページャ)を使用する(例:`git --no-pager`、`gh`のpager無効化)。

### 8.2 設計書(`docs/design.md` + `docs/design/`)の維持

- 設計書を用いて実装した場合、実装後にその内容と実装を比較し、差分があれば**該当する分冊**を最新化する。
- 上記の事後更新を支援するカスタムスラッシュコマンド `/save-design` を用意し、実装差分を検出して該当分冊への反映を提案させる。
- 新しい関心事は既存の分冊への追記を優先し、分冊が肥大化した場合にのみ分冊の追加を提案する。分冊構成を変更した場合は、ハブ(`docs/design.md`)の分冊索引と要件対応表も併せて更新する。

### 8.3 TDDの適用方針

本アプリは「決定的なコード(スクリプトのグルーロジック)」と「非決定的な処理(LLMによる議事録生成そのもの)」が混在するため、TDD(Kent Beck準拠、Red→Green→Refactor)の適用範囲を以下のように区別する。

| 対象 | TDDの適用 | 理由 |
|---|---|---|
| 引数パース、`.env`読み込み、ファイルパス生成、`--from-step`のステップ制御、SSOセッションの有効性チェックロジック等 | **通常のTDDを適用** | 入出力が決定的で、失敗/成功を明確に定義できる |
| `transcribe.py`(`faster-whisper`の呼び出し部分) | **呼び出しロジックはTDD対象、文字起こし精度は対象外** | 「正しく呼び出せているか」「出力ファイルが期待形式か」はテスト可能だが、認識精度はモデル依存のためテスト対象としない |
| ステップ1〜3の `claude -p` 呼び出し(議事録生成本体) | **呼び出しの境界(ラッパー関数)はTDD対象、生成内容の品質は対象外** | `claude`コマンドの呼び出しをラップする関数を用意し、テスト時はモックに差し替える。生成された議事録の品質は `/minutes-review` や人間によるレビューで担保する |

- 処理を変更するたびにテストを実行し、常にグリーンな状態を保つ。Formatter/Linterも常に通す。
- 使用ツール
  - Python(`transcribe.py`等):テスト `pytest`、Lint `ruff`、Format `black`
  - Bash(`generate_minutes.sh`等):テスト `bats`、Lint `shellcheck`、Format `shfmt`
- カバレッジは**決定的なコード部分に対して80%以上を目標**とする(100%を目指すことが望ましいが、プロンプトファイル・LLM生成部分の品質はカバレッジの対象としない)。
  - カバレッジ取得コマンド例:`pytest --cov`

### 8.4 タスクの完了条件

- 常にデグレード(既存機能の劣化)がないことを確認する。
- Format/Lint/Testが一貫して成功している。
- 決定的なコード部分のテストカバレッジが80%以上である。
